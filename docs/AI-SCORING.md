# AI 参考评分规范（vibecoding 过程与成果）

> 触发时机：参赛者执行 `--submit` 完成最终提交后，**自动**采集证据并计算参考分，上报到服务端存档（大屏与后台可见）。
> 定位：**AI 参考分**，供评委参考，**不替代人工评审**。所有分数必须能追溯到证据（文件、git 提交、服务端审计）。

---

## 0. 设计原则（为什么这样设计）

1. **证据优先于自述**：机器能判定的项（时序、提交历史、测试存在性、服务端审计）占主体权重，一律自动计算；
2. **主观项单列**：作品价值/创新性等无法机器判定的部分单独列出（15 分），标注「待评审」，不计入自动总分——避免 Agent 自评当实分；
3. **可复现**：同一份产物 + 同一份审计，任何人重跑 `--score` 应得到同一分数；
4. **红线优先**：发现违规（密钥入库、跳节点、删测试）直接扣分并在报告中点名。

满分 100 = **机器可判定 85** + **主观参考 15（单列，不计入自动分）**。

---

## 1. 维度与权重

### A. 需求与规格闭环（20 分，机器判定）

| 编号 | 评分点 | 分值 | 判定方法 |
|---|---|---|---|
| A1 | PRD 落盘且结构完整（目标用户/核心场景/输入输出/数据来源） | 5 | `docs/prd.md` 存在且命中 ≥3 个必需章节关键词 |
| A2 | 逻辑闭环：输入有来源、输出有去向 | 6 | PRD 含「数据来源/输入」「输出/去向」类章节，且非空（≥2 条） |
| A3 | 用户亲自参与需求（需求模板由用户填写） | 5 | `docs/requirements-template.md` 存在且用户填写部分非空（排除模板占位） |
| A4 | 不确定的数据/接口先验证再落地 | 4 | 存在验证记录（`docs/verification*.md` 或 PRD 中的「已验证」小节 + 脚本） |

### B. 工程纪律（24 分，机器判定）

| 编号 | 评分点 | 分值 | 判定方法 |
|---|---|---|---|
| B1 | SDD：规格先于实现 | 7 | `docs/prd.md` 的首次提交时间 ≤ 首次功能代码提交时间（git log 比对） |
| B2 | TDD：测试先于实现 | 7 | 存在测试文件，且其首次提交时间 ≤ 对应实现目录的首次提交时间；或 `docs/tdd-log.md` 记录了「先失败后通过」 |
| B3 | 提交粒度与信息质量 | 5 | 提交数 ≥8（粒度细）+ 中文主题占比、含正文说明「为什么」的提交占比 |
| B4 | 增量迭代 | 5 | 服务端 `loop_count ≥ 2` 且每轮有变更说明（审计/`docs/` 有记录）；单轮项目按基础分计 |

### C. 测试与质量保障（22 分，机器判定）

| 编号 | 评分点 | 分值 | 判定方法 |
|---|---|---|---|
| C1 | 自动化测试存在且有规模 | 6 | 测试文件数 ≥2 且断言总数 ≥20（零依赖脚本/框架均可） |
| C2 | E2E 覆盖核心旅程 | 5 | `hackathon.config.json` 的 `verify.e2e` 指向真实存在的命令/脚本 |
| C3 | 全量回归通过 | 6 | 仓库存在闸门证据文件且其 commit 与当前 HEAD 一致、断言 0 失败 |
| C4 | 独立评审且 P0/P1 清零 | 5 | `docs/review*.md` 存在且含 P0/P1 结论（无 P0/P1 或已标注清零） |

### D. 交付与上线（19 分，机器判定）

| 编号 | 评分点 | 分值 | 判定方法 |
|---|---|---|---|
| D1 | 部署成功、线上可访问 | 5 | 服务端部署记录 + 部署节点探活证据（审计 evidence） |
| D2 | 线上验收全绿 | 6 | 服务端验收审计：探活/接口/E2E 三关通过 |
| D3 | 稳定性 | 4 | 服务端被拒上报次数 ≤10 得满分，>10 得一半（口径与服务端审计统计 `stats.rejects` 一致） |
| D4 | 过程合规 | 4 | 无跳节点、无乱序上报、无违规上报（服务端审计） |

### E. 作品呈现（15 分，**主观参考，单列，不计入自动总分**）

| 编号 | 评分点 | 分值 | 判定方法 |
|---|---|---|---|
| E1 | 需求与实现一致（PRD 承诺的功能线上可演示） | 6 | 人工/评委复核，Agent 可提供对照说明作参考 |
| E2 | 开箱可体验（入口清晰、无需额外说明） | 5 | 人工/评委复核 |
| E3 | 完成度与创新性 | 4 | 人工/评委复核 |

## 2. 红线扣分（机器判定，直接从总分中扣）

| 编号 | 违规 | 扣分 | 判定方法 |
|---|---|---|---|
| R1 | 密钥/凭据进入 git（`.env`、`hackathon.config.json`、密钥字段） | −10 并点名 | `git ls-files` 命中敏感文件名/内容 |
| R2 | 跳节点、乱序上报 | 每次 −1，上限 −5 | 服务端审计 `STAGE_OUT_OF_ORDER` 计数 |
| R3 | 刷上报（触发限频） | −3 | 服务端审计 `RATE_LIMITED` 计数 >10 |
| R4 | 削弱测试（测试数或断言数减少） | −5 | 与提交前基线比对（测试文件数/断言数下降） |

扣分总和不设下限保护：最低 0 分。

---

## 3. 自动总分与呈现

```
自动总分 = clamp(A + B + C + D − 红线扣分, 0, 85)
报告结构 = 自动总分 + 各维度明细（含证据行）+ 红线命中 + 主观项（E，标注「待评审」）
```

- 报告的每一项都必须附**证据行**（文件路径、git hash、服务端审计 ID/时间），无证据项不得分；
- 服务端存储：`projects.ai_score`（自动总分）、`projects.ai_score_detail`（完整 JSON 报告）、`ai_scored_at`；
- 呈现：大屏「已提交作品」榜显示参考分徽标；管理后台项目表显示分数，可查看明细；
- 官方成绩仍以评委人工评审为准，AI 参考分仅作输入之一。

## 4. 争议与边界处理

| 情况 | 处理 |
|---|---|
| 单轮项目（未 `--loop`） | B4 按基础分（3/5）计，不视为缺陷 |
| 纯静态站 / 接口项目 | C2 可用零依赖 HTTP 脚本满足，不强制浏览器 E2E |
| 团队未使用 skill 流程（无 PRD 等） | A、B 项按实际证据计分，不推断不臆造 |
| 证据缺失 | 该项 0 分，并在报告中标注「证据缺失」，不做善意推定 |
| 人气值 | **不计入自动评分**（人气受现场人数与围观影响，不反映工程质量；作为独立展示指标供评委参考） |
| 报告重跑 | 允许 `--score` 重算（以最后一次为准），历史留审计 |
